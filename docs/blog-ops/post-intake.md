# 文章归档与维护流程

把 `inbox/` 里的原稿归档进 `src/content/posts/`，补全分类、专栏、摘要，并按
[display-rules.md](./display-rules.md) 做窄栏适配。适用于任何 AI 编码工具，Claude Code
里可以用 `/post-intake` 触发。

**授权范围**：这份流程授权你直接改动稿件的排版、标题长度、表格结构和 Frontmatter，
不需要逐条确认。它不授权你改写作者的观点和语气、补充作者没有写过的经历或结论、
把文章从草稿改成发布状态。

## 1. 读稿与定位

通读全文。确认主题、文章类型（问题分析 / 技术教程 / 实践复盘 / 工具体验 / 随笔 /
读书笔记）和目标读者。不要只看标题和小标题就开始归档——分类、专栏和摘要都依赖对
全文的判断。

带图片的稿件通常是 `inbox/某篇文章/` 这样的子目录，正文文件名不固定。

## 2. slug 与目录

1. 定 slug：小写英文数字加连字符，用主题关键词，稳定、可读、不含日期。中文标题取
   语义对应的英文词，不用拼音堆叠。参考 `scripts/create-post.ts` 导出的 `toSlug`。
2. 建 `src/content/posts/<slug>/`。
3. 正文移进去并改名 `index.md`（含 MDX 语法时用 `index.mdx`）。
4. 图片移进同一目录，文件名改成英文小写连字符，正文里的引用同步改成 `./name.png`。
5. `inbox/` 未纳入版本管理，从 inbox 移出用 `mv`；重命名已入库的文章用 `git mv`。

同名目录已存在时停下来问，不要覆盖。

## 3. 分类

从 `src/.config/user.ts` 的 `categoryMap` 里选，**优先落进已有分类**：
随笔、读书、英语、AI、编程、工程实践。

- 一般给一个分类；确实横跨两个领域时最多两个。
- 「编程」偏语言、工具链、代码本身；「工程实践」偏部署、运维、系统搭建；「AI」偏模型、
  RAG、Agent 这类主题；「随笔」偏生活与个人思考；「读书」「英语」按内容归类。
- 需要新分类时，同时在 `categoryMap` 里补 `{ name, path }`，`path` 用英文小写连字符。
  不这么做会生成中文 URL。

## 4. 专栏与顺序

只有属于长期主题时才进专栏，不为单篇文章新建专栏。现有专栏见 `seriesMap`；若
`seriesMap` 为空，先不要给文章加 `series`。

1. 判断是否属于某个现有专栏。
2. 属于的话，把 `series.name` 写成专栏名即可。专栏页按发布时间排列，不必再写
   `series.order`；如果以后需要固定阅读顺序，再补大于 0 的整数 `order`。
3. 确实需要新专栏时，在 `seriesMap` 里补 `{ name, path, description }`，专栏描述一句话
   说明它覆盖什么。

## 5. Frontmatter

字段定义见 `src/content.config.ts`。归档后应该长这样：

```text
---
title: '文章标题'
pubDate: 2026-07-25
description: '80~120 个汉字的完整摘要。'
categories: ['编程']
series:
  name: 'Python 工具链'
  order: 3
draft: true
---
```

- `title` 沿用作者的标题，只在超出长度上限时压缩。
- `pubDate` 用稿件里已有的日期，没有就用当天。
- `description` 按 [display-rules.md](./display-rules.md) 写 80~120 个汉字，不复述标题。
- **`draft` 一律先设 `true`**。只有作者明确说发布，才改成 `false`。

## 6. 窄栏适配

按 [display-rules.md](./display-rules.md) 直接改，重点四项：

1. **标题**：主标题压到 16 个汉字内，二级标题 20 个汉字内，清掉 `####` 及更深层级和跳级。
2. **表格**：超过 3 列、单元格超过 10 个汉字、单元格里塞了公式或列表的，改成 2~3 列，
   或者拆成「小标题 + 要点列表」。改完在报告里说明动了哪几张表、怎么改的。
3. **段落**：超过约 200 个汉字的段落按逻辑切开。
4. **图片与链接**：路径、文件名、裸链接。

改动只动表达形式，不动论述内容和结论。作者的判断、语气、举例都保留；不确定某处是
表达习惯还是排版问题时，保留原样并写进报告。

## 7. 校验

```bash
pnpm theme:check <slug>   # 只查这篇，必须零 error、零 warning
pnpm theme:check          # 查全部，用来看存量文章的欠账
pnpm build                # 构建必须通过
```

带 slug 的那条是归档流程的验收标准。不带参数会带出存量文章的历史问题，那些不在本次
改动范围内，不要顺手改。

`theme:check` 覆盖文件名、slug、必填字段、摘要字数、标题宽度、表格列数与单元格宽度、
标题层级、图片路径、分类与专栏映射、order 冲突。它只检查可枚举的规则，通过不等于
排版已经好读。涉及表格或图片的明显版式改动，再用 `pnpm dev` 看一眼实际页面。

## 8. 交付报告

报告包含：

- 归档位置和最终 URL
- 分类、专栏、order 的结果和理由
- 生成的 `description`
- 窄栏适配都改了什么（尤其是重构过的表格和改短的标题）
- `theme:check` 与 `build` 结果
- 仍需作者确认的地方，以及为什么保持 `draft: true`

## 维护已发布文章

同一套规则也用于维护存量文章，但有两条额外约束：

- **不擅自改已发布文章的目录名**。改 slug 会断掉已有链接，先报告问题让作者决定。
- 改动已发布文章的正文时，顺手补 `modDate`。
