当 Cursor 可以自己搜索代码、修改文件、运行测试之后，一个新的问题很快会出现：我们不再缺少能执行任务的 Agent，开始缺少的是组织任务的方法。

一个 Agent 正在开发功能，另一个 Bug 又需要调查；几个任务同时修改同一仓库，文件很容易互相覆盖；每次打开新对话，都要重新解释项目结构、代码规范和检查命令；同样的发布检查做了很多次，下一次仍然要从头说明。

这也是 Cursor 最近大量新功能容易让人困惑的原因。Agents Window、Worktree、Subagent、Cloud Agent、Rules、Memories、Skills、MCP、Plugins、Loop 和 Automations 并不是一组并列的小功能。它们分别在解决几类更大的问题：

- 怎样同时推进多个任务，又不让修改互相干扰；
- 怎样让 Agent 持续得到正确的项目知识；
- 怎样把重复做过的工作沉淀下来；
- 怎样让稳定任务在后台或触发条件下运行；
- 当 Agent 自主权越来越大时，怎样保留必要的控制。

如果仍然把 Cursor 当聊天框，这些功能确实显得又多又散。换成“开发工作流”的角度，它们的关系会清楚很多。

## Agents Window 如何组织任务

传统编辑器以文件为中心。我们打开一个项目，在文件树、编辑区和终端之间切换。早期 Cursor 只是在这个界面旁边增加了聊天，所以即使 Agent 能够修改代码，我们仍然习惯把它看成编辑器里的一个附加面板。

Cursor 3 的 Agents Window 更像一个任务工作台。根据[官方介绍](https://cursor.com/changelog/3-0)，本地、Worktree、Cloud 和远程 SSH 环境中的 Agent 都可以出现在同一个界面中。每个任务有自己的对话、计划、终端、Diff、浏览器和运行环境。

这里最重要的变化不是布局，而是组织方式。

以前一个聊天可能从“理解项目”开始，中间做了搜索功能，后来又顺手修了构建错误，几天后继续用它讨论部署。上下文越来越长，任务边界越来越模糊。现在更合适的方式是让一个主要对话负责一个可以描述清楚的结果：

- “增加文章标题搜索”是一个任务；
- “调查生产环境图片 404”是另一个任务；
- “升级 Astro 并修复兼容问题”再单独建立任务。

任务完成后，对话的主要使命也就结束。以后需要相关结论，可以搜索历史对话或把稳定知识写进规则，而不是让一个聊天无限增长。

Agents Window 的平铺布局适合同时观察几个任务，但并不代表每件事都要开一个 Agent。比如主任务正在实现搜索功能，临时想确认某个搜索库是否支持中文，可以使用 Side Chat 做只读调查，不打断主对话。Side Chat 会继承主任务的上下文，又能保持独立，适合问旁支问题、比较方案和检查判断。[Cursor 对 Side Chats 的介绍](https://cursor.com/changelog)也把它定位为在主任务旁边进行研究，而不是默认启动另一组修改。

一个很实用的原则是：

> 按交付结果划分任务，不要按想到问题的时间把所有内容堆进同一个聊天。

界面只是帮助我们看见多个任务，真正决定工作是否清楚的仍然是边界。

## 三种并行能力怎么选

Worktree、Subagent 和 Cloud Agent 都能让任务同时运行，但它们隔离的不是同一种东西。

| 能力 | 主要解决什么 | 典型场景 |
| --- | --- | --- |
| Worktree | 隔离代码目录和 Git 分支 | 两个任务要同时修改同一仓库 |
| Subagent / Multitask | 拆分任务和调查方向 | 并行搜索、比较方案、执行独立子任务 |
| Cloud Agent | 隔离执行环境和运行时间 | 长任务、后台运行、不占用本地电脑 |
| Multi-root Workspace | 把多个仓库放进一个任务上下文 | 前端、后端和共享库需要一起修改 |

**Worktree 适合“代码会打架”的情况。**

Git Worktree 会从同一个仓库创建独立目录和分支。Agent A 修改搜索功能，Agent B 修复归档页面，它们不会同时操作本地同一批未提交文件。完成后，再分别检查和合并。

一个小例子：本地正在写一篇文章，突然发现博客构建失败。直接让 Agent 在当前目录修复，可能把正在编辑的文件也包含进修改和提交。把“修复构建错误”放进 Worktree，Agent 可以在干净分支中调查，当前工作不受影响。

Cursor 3.2 已经把 Worktree 和多任务管理放进 Agents Window，也可以用 `/worktree` 启动隔离任务。[官方更新](https://cursor.com/changelog/04-24-26)还支持把完成的分支移动回本地前台测试。

Worktree 不是没有代价。两个任务如果都修改同一个核心文件，最后仍然会发生合并冲突。它解决的是工作过程中的互相覆盖，不会自动消除任务本身的依赖。

**Subagent 适合“问题可以拆开”的情况。**

例如准备升级一个框架，可以把调查工作拆成几份：

- 一个 Subagent 阅读官方升级说明，整理破坏性变化；
- 一个检查项目中使用了哪些受影响 API；
- 一个查看依赖是否支持目标版本；
- 主 Agent 根据这些结果制订迁移计划。

这些子任务输入清楚，输出都是报告，不会互相覆盖代码。`/multitask` 还可以把排队任务拆给异步 Subagent 并行处理。

Subagent 最适合边界清楚的工作，不适合把同一句“实现这个功能”同时发给几个 Agent，除非我们的目的就是比较不同方案。否则它们会重复搜索、重复修改，最后产生几份难以整合的结果。

**Cloud Agent 适合“任务不该占住本地”的情况。**

完整测试需要运行很久、CI 问题要持续观察、依赖环境比较重，或者自己准备关电脑，这些都适合交给云端。Cloud Agent 会在独立虚拟机中工作，可以安装依赖、运行程序并生成截图、日志或演示。

近期 Cursor 还支持用 `/in-cloud` 启动云端子任务，并在本地和云端之间交接会话。[Cloud Agent 更新](https://cursor.com/changelog/cloud-in-agents-window)允许把配置完成的环境保存为快照，后续任务不用每次重新安装全部依赖。

一个小例子：本地已经完成修改，但完整端到端测试要运行四十分钟。可以把计划和当前分支交给 Cloud Agent，让它执行测试、调查失败并给出结果，自己继续处理其他工作。

选择方法其实很简单：修改会不会互相覆盖，决定是否需要 Worktree；任务能不能独立拆分，决定是否使用 Subagent；执行是否需要独立环境或较长时间，决定是否交给 Cloud Agent。它们可以组合，但没有必要为了显得“Agent 化”而全部启用。

## 多 Agent 应该怎样拆任务

并行最容易带来一种错误期待：既然一个 Agent 能完成任务，五个 Agent 应该能把速度提高五倍。

软件开发很少这么线性。几个 Agent 同时推进的前提，是任务确实能够分开。

适合并行的工作通常有以下特点：

- 输入和目标比较明确；
- 修改范围相对独立；
- 不依赖另一个任务尚未产生的决定；
- 每份结果可以单独验证；
- 最终整合成本低于节省的时间。

不适合并行的情况也很常见。

需求还没确定时，不要让多个 Agent 同时实现；接口还没设计好时，不要把前端和后端完全分开；几个任务都要重写同一个核心模块时，Worktree 只会把冲突推迟到合并阶段；一个任务必须使用另一个任务的结果时，应该串行而不是并行。

可以把常见拆分方式分成三类。

**按调查方向拆分。** 这是风险最低的并行方式。一个 Agent 查代码，一个查文档，一个查运行日志，最后由主任务汇总。因为输出主要是信息，不容易产生代码冲突。

**按独立模块拆分。** 例如已经确定 API 后，一个任务实现后端接口，一个任务实现前端界面，一个任务补测试。前提是接口契约足够明确。

**按候选方案拆分。** 对难题让几个 Agent 在独立 Worktree 中分别尝试，然后比较正确性、复杂度和验证结果。这不是为了把结果全部合并，而是选择最好的一个。

举一个较大的例子：要给博客增加搜索、标签页和阅读统计。如果三项之间没有共同的数据模型变化，可以分别放进 Worktree。如果它们都依赖一次内容层重构，就应该先由一个任务完成并稳定内容接口，再并行开发上层功能。

所以真正提升并行效率的不是多开窗口，而是先看清依赖关系。人的角色会从逐步操作代码，转向定义任务、约定接口、安排先后和验收整合。

## 上下文能力如何分工

多个 Agent 能够同时工作后，项目知识会成为新的问题。

每次开新任务都重新说明“这是 Astro 博客”“文章放在这个目录”“图片必须使用相对路径”“修改后运行 `pnpm build`”，既浪费时间，也容易漏掉要求。Cursor 提供的 Rules、Memories、Skills、MCP 和 Plugins，都是在解决上下文和能力复用，但它们适合承载的内容不同。

**Rules 记录长期约束和项目事实。**

Project Rules 存放在 `.cursor/rules` 中，可以进入版本控制，也可以根据文件路径决定什么时候应用。[官方文档](https://docs.cursor.com/context/rules)建议用它保存项目领域知识、工作流、格式和架构约定。

一条博客项目规则可以写：

```text
文章规范：
- 文章存放在 src/content/posts/<slug>/index.md；
- Frontmatter 必须包含 title、pubDate、categories 和 draft；
- 文章图片与 index.md 放在同一目录，使用相对路径引用；
- 修改内容或页面后必须运行 pnpm build。
```

Rule 应该具体、稳定、可执行。“请写高质量代码”没有太大作用；“新增页面优先复用 `LayoutDefault.astro`，不要创建第二套页面宽度样式”更有用。

也不要把所有规则设成全局始终加载。后端数据库规范对修改博客样式没有帮助。按目录和用途拆分，让相关任务加载相关规则，效果通常更好。

**Memories 保存协作中发现、以后仍可能有用的信息。**

例如经过一次讨论确定“搜索第一版只匹配标题和正文，不支持拼音”，这个决定可能会影响后续任务。Cursor 可以从对话中提取记忆，也可以明确要求它记住。[Memories 文档](https://docs.cursor.com/en/context/memories)强调记忆会跨会话保留，并在保存前由用户确认。

Memory 需要定期整理。项目决策会变化，之前正确的信息可能过期。如果新方案已经支持拼音，旧 Memory 仍然说“不支持”，它就会变成错误上下文。

**Skills 记录一类任务的完成方法。**

Rule 说“文章必须包含哪些字段”，Skill 则可以说“创建一篇文章时按什么流程做”：先查资料，建立目录，生成 Frontmatter，检查图片，运行构建，最后输出检查结果。

一个发布检查 Skill 可以包含：

```text
1. 检查 Frontmatter 必填字段；
2. 检查本地图片和内部链接；
3. 运行 pnpm build；
4. 在浏览器打开文章页面；
5. 输出错误、警告和人工确认项。
```

当同一种任务已经重复做过几次，而且步骤比较稳定时，才值得整理成 Skill。第一次做就急着抽象，往往会把还没验证的流程固化下来。

**MCP 让 Agent 获得代码仓库之外的上下文和工具。**

模型默认看不到线上监控、数据库、设计稿、项目管理系统和团队文档。MCP 可以把这些系统作为工具接入 Cursor。官方列出的 MCP 类型包括 GitHub、Figma、Linear、Sentry、Playwright、数据库和部署平台等。[MCP 列表](https://docs.cursor.com/en/tools/mcp)

例如调查线上错误时，只贴一张 Sentry 截图只能得到静态信息；通过 MCP，Agent 可以查询错误事件、相关版本和堆栈，再回到代码中定位。修复完成后，还可以查询部署状态或运行浏览器测试。

接入 MCP 也意味着增加权限。只读查询和修改生产系统不是同一风险等级。安装之前要看清它能访问什么，敏感操作尽量保留审批。

**Plugins 适合把一整套能力打包。**

一个 Plugin 可以组合 Skills、MCP、Rules、Commands、Subagents 和 Hooks，适合团队共享一套完整工作方式。比如“前端发布插件”可以同时包含设计系统规则、浏览器检查 Skill、部署 MCP 和专门的审查 Agent。

Cursor 现在通过 Customize 页面统一管理这些能力，可以放在用户、团队或工作区层级。[Customize Cursor](https://cursor.com/changelog/customize)使 Plugin 更接近一个可安装的工作流包，而不是单独的一段提示词。

判断应该使用哪一种，可以记住下面这组关系：

| 需求 | 更适合放在哪里 |
| --- | --- |
| 当前任务的特殊要求 | 当前任务说明 |
| 每次都要遵守的项目约束 | Rules |
| 对话中形成的长期项目事实 | Memories |
| 重复任务的标准步骤 | Skills |
| 外部系统的数据和操作 | MCP |
| 一整套需要安装和共享的能力 | Plugins |

这些能力的目标不是让配置看起来复杂，而是减少重复说明，同时让不同 Agent 按同一套标准工作。

## 上下文重在相关

当 Rules、Skills、MCP 和 Memories 越积越多，很容易产生一个错觉：上下文给得越多，Agent 就越懂项目。

实际上，无关上下文会降低信号。修改一个 CSS 问题时加载完整数据库规范没有帮助；十几个 MCP 同时可用，Agent 还要先判断该调用哪个；一个持续几周的聊天里可能同时存在旧方案和新决定；过期 Memory 会让错误信息显得像长期事实。

Cursor 已经可以显示 Agent 的上下文使用明细，查看系统提示、Rules、Skills、MCP 和 Subagents 分别占用多少内容。[Context Usage Breakdown](https://cursor.com/changelog/05-06-26)适合排查“明明配置很多，Agent 为什么反而容易忽略要求”这类问题。

管理上下文时，可以做几件实际的事。

第一，Rule 尽量短而明确，大规则按模块拆开。第二，能按路径自动应用的规则，不要全部设为 Always。第三，一个对话处理一个主要任务，方向已经完全变化时新建任务。第四，定期删除过期 Memory。第五，只为当前工作启用需要的 MCP 和 Skill。

还要区分“长期上下文”和“任务状态”。代码规范适合写进 Rule，当前报错日志不适合；发布流程适合做成 Skill，某次构建的临时错误不适合。后者应该放在当前任务里，用完就结束。

可以把上下文理解成代码依赖：需要时精确引入，比在全局挂载所有东西更容易维护。

## 从手动任务到自动化

自动化很有吸引力，但并不是所有能交给 Agent 的事情都值得自动运行。

一个比较稳妥的演进顺序是：

> 手动完成一次 → 重复几次并修正流程 → 整理为 Skill → 短期持续运行用 Loop → 触发条件稳定后再做 Automation。

**手动阶段**用来确认问题是否真的可重复。比如第一次检查文章链接时，先看看有哪些特殊情况：代码块中的 URL 要不要检查，草稿是否包含在内，外部网站超时算错误还是警告。

**Skill 阶段**把已经验证过的步骤固化下来，但仍由人主动发起。这样可以继续观察流程，发现问题就修改，不会自动影响所有任务。

**Loop 适合当前任务中的持续等待或迭代。** 例如“每五分钟检查一次部署，成功后打开页面验证”“继续修复直到这组测试通过”。它有明确结束条件，主要解决任务需要等待或重复几轮的问题。

**Automation 适合长期、事件驱动的工作。** Cursor Automations 可以按时间运行，也可以由 GitHub、Slack、Linear、PagerDuty 和 Webhook 等事件触发。任务会在云端环境中执行，并使用配置好的模型和 MCP。[官方介绍](https://cursor.com/changelog/03-05-26)把它称为 always-on agents。

近期 Cursor 还加入了 `/automate`，可以在本地会话中用自然语言创建自动化，并支持更多 GitHub、Slack 触发和 Computer Use。[Cursor 3.8 更新](https://cursor.com/changelog/06-18-26)

判断一项工作是否适合自动化，可以问五个问题：

1. 触发条件是否明确？
2. 输入是否能够稳定获取？
3. 正确结果是否可以验证？
4. 失败时是否有安全的停止方式？
5. 即使判断错误，影响范围是否可控？

“每天自动重构项目代码”不适合作为起点，因为目标和验收都不清楚。“每次文章 PR 更新后检查 Frontmatter、内部链接和构建”就合适得多。

## 完整案例：文章发布检查

假设我们要为这个博客建立文章发布检查。目标不是让 AI 自动决定文章内容好不好，而是把重复、可验证的检查交出去，让人把精力放在表达和最终判断上。

第一步先手动梳理流程。

一篇文章发布前，需要确认 Frontmatter 完整、日期格式正确、本地图片存在、内部链接有效、Markdown 可以被解析、生产构建通过，最终页面在桌面和移动端可读。内容观点、表达取舍和是否值得发布仍然由作者决定。

第二步整理上下文。

把长期不变的文章结构、图片路径和构建要求写进 Project Rules。把“如何检查一篇文章”的操作顺序整理成 Skill。这样无论本地 Agent、Worktree 任务还是云端任务执行，得到的标准都是一致的。

第三步设计任务拆分。

Frontmatter 和资源链接可以由一个 Agent 静态检查；构建和页面验证可以由另一个任务执行。如果需要自动修复，把修改放进 Worktree，避免直接改变作者正在编辑的文件。对于一篇普通文章，没必要开很多 Agent；对于一次包含大量历史文章的迁移，并行检查才有意义。

第四步运行和验证。

Agent 执行 `pnpm build`，读取错误。如果构建通过，再在浏览器打开文章，检查标题、代码块、图片、目录和移动端宽度。最终输出一份报告：

```text
通过：
- Frontmatter 字段完整；
- 本地图片均存在；
- 生产构建通过；
- 桌面端和 390px 移动端页面可正常阅读。

需要确认：
- 有两个外部链接请求超时；
- 文章发布日期晚于当前日期；
- 第一张图片缺少说明文字。
```

这里“需要确认”很重要。工具无法可靠判断的内容，不应该为了追求全自动而强行给出结论。

第五步再考虑触发自动化。

手动运行几次，确认规则和 Skill 足够稳定后，可以设置 GitHub Automation：当包含文章目录修改的 Pull Request 创建或更新时启动检查。安全问题可以自动修复并准备单独提交，外部链接超时、日期异常和内容问题只生成评论，由作者决定。

如果发布过程涉及多个仓库，例如博客源码和独立搜索服务，可以使用 Multi-root Workspace；如果完整构建耗时较长，可以交给 Cloud Agent；如果某项检查失败，可以用 Loop 等待修复后的部署重新完成。

这样组合以后，每个功能都有明确位置：

- Agents Window 管理任务；
- Worktree 隔离修改；
- Subagent 负责可拆分的检查；
- Cloud Agent 提供后台执行环境；
- Rules 保存项目标准；
- Skill 保存检查步骤；
- MCP 连接 GitHub、部署或监控；
- Automation 负责在正确时间启动。

这是一条可维护的流程，而不是一条越来越长、每次都要重新复制的提示词。

## 设计好权限、成本和验收

Agent 越能自主执行，边界就越重要。

本地聊天中的错误修改通常很快能看到；Cloud Agent 在后台运行几个小时，可能已经进行了多轮操作；MCP 接入 GitHub、数据库或部署平台后，Agent 的行为会影响外部系统；Automation 配置错误，可能在每次事件发生时重复执行。

至少要明确四件事：

- **为什么启动**：时间、事件还是人工指令；
- **能够访问什么**：仓库、网络、密钥和外部服务；
- **怎样算完成**：测试、构建、页面验证还是人工确认；
- **什么时候停下**：失败次数、运行时间、危险操作和无法判断的情况。

只读调查和直接写入生产数据库不应该使用同一权限。能在 Worktree 中完成的修改，不必直接写主分支。能够先生成报告的自动化，不必第一版就开放自动合并。

Cursor 的 Auto-review Run Mode 可以自动允许白名单操作，把适合沙箱运行的调用放进沙箱，其余操作再判断是否需要审批。这能减少机械确认，但不能替代权限设计。删除数据、使用生产密钥、发布上线、修改账单或访问敏感信息，仍然应该保留明确审批。

成本同样需要设计。多开 Agent 并不免费，长对话和过量上下文也会增加消耗。一个没有计划的模糊任务同时跑五份，通常不如先花几分钟明确边界，再把真正独立的部分并行。

好的 Agent 工作流不是“尽量不让人参与”，而是让人只参与真正需要判断的地方。重复搜索、运行检查和整理结果可以交出去；目标、风险、权限和最终接受仍然应该有人负责。

## 沉淀可复用的工作方法

Cursor 的功能还会继续变化，入口、名称和可用范围也会调整。如果只是记住某个按钮在哪里，每次大版本更新后都要重新学习。

更稳定的理解是：

- 任务互相干扰，用隔离解决；
- 问题能够拆分，用并行解决；
- 工作耗时或需要后台执行，用云环境解决；
- 项目要求总在重复，用 Rules 和 Memories 沉淀；
- 同类任务步骤稳定，用 Skill 复用；
- 需要外部数据和操作，用 MCP 扩展；
- 触发和验收已经清楚，再用 Automation 持续运行。

这些方法不只适用于 Cursor。换成 Codex、Claude Code 或之后出现的其他 Agent 工具，名称和界面会不同，但任务拆分、上下文、权限、验证和自动化仍然是同一组问题。

AI 编程真正提高效率的地方，也不只是把一段代码生成得更快，而是把原来靠人反复协调的开发过程，逐渐整理成边界清楚、结果可验收、能够重复运行的工作单元。

工具负责执行得越来越多，人就更需要把工作设计清楚。
