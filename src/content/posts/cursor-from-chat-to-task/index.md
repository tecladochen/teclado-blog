最近更新 Cursor 后，我发现自己有点不会用了。

不是找不到聊天框，也不是不知道怎么让它改代码。恰恰相反，这些我已经很熟悉了：选中代码，描述需求，让 Cursor 生成修改；结果不对就补一句，再让它改一次。

问题是 Cursor 里出现了越来越多新东西：Ask、Plan、Debug、Agents Window、Worktree、Cloud Agent、Rules、Skills、MCP……每个名词单独看都不难理解，真正回到项目里，我还是只会打开一个聊天，输入“帮我实现这个功能”。

这种感觉很像拿到一台可以完成整套工作的机器，却一直只把它当成一个问答框使用。

所以我重新看了一遍 Cursor 最近的功能，也重新整理了自己的使用方式。最后发现，需要学习的不只是新按钮放在哪里，而是先换掉一个旧的理解：**Cursor 的核心已经从“生成代码”变成了“执行开发任务”。**

这两个说法看起来差不多，实际对应的是两种完全不同的工作方法。

## 从生成代码到完成任务

过去使用 Cursor 时，一次交互的目标通常是得到一段答案。

例如遇到一个报错，把错误信息贴进聊天；想写一个组件，告诉它组件需要有哪些字段；想重构一个函数，选中代码让它修改。Cursor 负责生成，人负责找到正确文件、补充项目背景、运行代码、发现问题，再回来进行下一轮提问。

在这种模式下，AI 只是开发过程中的一个环节。真正把零散回答连接成结果的人还是自己。

现在的 Agent 已经可以搜索代码库、读取多个文件、编辑代码、执行终端命令、观察输出，并根据错误继续修改。[Cursor 对 Agent 的说明](https://docs.cursor.com/en/agent/overview)里，重点也不再是“回答编程问题”，而是独立完成复杂的编码任务。

能力变了，交给它的工作也应该变。

以前我们可能会说：

> 帮我写一个文章搜索组件。

现在更适合说：

> 调查当前博客的内容加载方式，为文章列表增加本地搜索。搜索需要匹配标题和正文，不能改变现有文章 URL，尽量复用当前组件和样式。开始修改前先给出实现方案，完成后运行构建，并在浏览器里检查搜索结果和移动端布局。

第一种要求的交付物是一段代码。第二种要求的交付物是一个能在现有项目里正常工作的功能。

这里真正增加的不是提示词长度，而是目标、约束和完成标准。只说“写一个搜索组件”，Cursor 很容易直接生成一个看起来正确的组件，但它不知道数据从哪里来，不知道项目是否允许增加依赖，也不知道什么状态才算完成。要求它交付一个功能，就必须让它接触真实项目，并对最终结果负责。

这也是现在使用 Cursor 最重要的变化：**不要把它当作一个需要逐句指导的代码生成器，而要把它当作一个能执行任务、但需要明确目标和验收条件的开发者。**

它可以替我们完成很多过程，但它不能替我们决定到底想做什么。

## 四种工作模式怎么选

以前我经常在一个聊天里做完所有事情：先问项目结构，接着讨论方案，聊到一半顺手让 Cursor 开始修改，运行报错后又在原来的对话里调试。对话一长，前面只是讨论过但没有采用的方案，也可能继续留在上下文里影响后面的修改。

Cursor 把工作分成不同模式，不只是界面设计，而是在区分开发中本来就不同的几个阶段。

| 模式 | 主要用途 | 适合什么时候用 |
| --- | --- | --- |
| Ask | 理解和调查 | 不清楚项目现状、调用关系或影响范围时 |
| Plan | 拆解和选择方案 | 需求涉及多个文件、存在多种做法时 |
| Agent | 执行和验证 | 目标、范围和完成条件已经相对明确时 |
| Debug | 收集运行证据、定位根因 | 错误难复现、静态阅读找不到原因时 |

**Ask 的价值是先得到事实。**

比如想修改登录逻辑，但不知道项目在哪里处理身份状态，可以先问：

> 只调查，不修改代码。找出用户登录状态从哪里读取，登录失效后经过哪些模块跳转到登录页，并列出相关文件。

这比直接说“修复登录跳转”可靠得多。后者会让 Agent 一边猜项目结构一边修改，前者则先建立一张基于真实代码的地图。

如果自己已经知道具体入口，也不必让 Agent 扫描整个项目，可以直接提供精确上下文：

> 阅读 `src/middleware.ts` 和登录页面，只分析未登录用户的重定向流程。

Cursor 的[上下文指南](https://docs.cursor.com/en/guides/working-with-context)把上下文分成两类：一类是意图，也就是我们想得到什么；另一类是状态，也就是项目现在是什么样。很多失败的提问只有意图，没有状态。我们说清楚了“把按钮变绿”，却没有让它看到按钮由哪个组件和哪套主题变量控制。

**Plan 的价值是把修改成本放到写代码之前。**

如果一个任务只有明确的一处改动，例如把超时时间从 10 秒改成 30 秒，没有必要先写一份长计划。但只要任务涉及多个模块、存在技术选择，或者自己也没有想清楚怎么做，Plan 通常都值得使用。

例如：

> 为博客增加全文搜索，先比较“构建时生成索引”和“客户端直接加载文章摘要”两种方案。说明它们对构建体积、首次加载、中文搜索和现有内容结构的影响，给出推荐，但先不要修改。

计划阶段最适合纠正方向。等 Agent 已经创建了几个文件、引入了依赖、改了页面结构，再说“不想这样实现”，返工成本会高很多。

Cursor 的 Plan 现在可以保存成文件，能够编辑，也能包含待办事项和 Mermaid 图。[相关更新](https://cursor.com/changelog/2-2)让计划不再只是聊天中一段看完就消失的文字。对于稍大的功能，可以先把计划改到自己认可，再开始执行。

**Agent 的价值是完成过程，而不只是生成代码。**

一个适合交给 Agent 的小任务可以是：

> 修复归档页面年份排序错误。先找到排序发生的位置，修改后运行现有检查；如果没有覆盖该行为的测试，补一个最小测试。

任务不大，但包含了调查、修改和验证。我们不需要告诉它具体该改哪一行，因为寻找正确位置就是任务的一部分。

**Debug 的价值是用运行事实代替猜测。**

有些问题读代码很难发现，例如某个状态偶尔被覆盖、请求顺序不稳定、页面只在特定操作后出错。如果只是反复把错误交给模型，它很可能根据常见原因不断猜测。Cursor 的 Debug Mode 会加入运行时日志，复现问题，再根据真实执行路径寻找根因。[官方介绍](https://cursor.com/changelog/2-2)强调的也是通过运行数据处理难定位的问题。

一个合适的 Debug 任务应该包含复现步骤：

> 打开文章列表，先选择分类 A，再快速切到分类 B，此时偶尔会显示 A 的结果。请用 Debug Mode 记录筛选状态和请求返回顺序，复现后定位根因，不要先根据代码猜测。

模式不是越高级越好，关键是当前的不确定性在哪里。不知道项目结构，用 Ask；不知道选哪种方案，用 Plan；方案已经明确，用 Agent；代码和预期不一致却找不到原因，用 Debug。

## 任务应该拆到什么程度

会使用 Agent 后，很容易走向两个极端。

一种是拆得太碎：让 Cursor 创建文件，再让它写函数，再让它补类型，再让它运行命令。这样虽然每一步都可控，但人仍然在承担全部流程管理，Agent 只是一个速度更快的键盘。

另一种是给得太大：

> 帮我把这个项目优化一下。

“优化”可能指性能、结构、可读性、依赖、页面体验或者构建速度。Agent 只能自己选择目标，最后往往改了很多地方，却不一定解决我们真正关心的问题。

比较合适的任务粒度是：**目标能够独立验收，范围又足够明确。**

下面几个对比比较直观：

| 太碎 | 合适 | 太大 |
| --- | --- | --- |
| 给这个函数加一个参数 | 为文章查询增加分类过滤，并补充对应测试 | 重构整个内容系统 |
| 创建一个搜索框组件 | 为文章列表增加标题搜索，包含空结果状态 | 做一个完整搜索系统 |
| 运行构建看看 | 修复当前构建错误，说明根因并验证构建通过 | 解决项目所有问题 |

一个简单判断方法是：任务完成后，能不能用一句明确的话判断它成功或失败。

“项目变得更好”无法验收；“文章列表可以按标题搜索，清空关键词后恢复全部文章”可以验收。“重构代码”无法验收；“把三个重复的日期格式化实现合并为一个工具函数，输出保持不变，现有测试通过”可以验收。

任务边界越明确，Agent 越容易自主工作。边界不明确时，给它更长的运行时间通常不会解决问题，只会让修改范围继续扩大。

## 怎样提供有效上下文

除了目标不清楚，另一个常见问题是上下文不对。

模型不知道我们的项目。它能看到哪些文件、日志、规则和对话，就根据这些信息做判断。上下文太少，它会用训练数据里的常见项目结构补全；上下文太多，无关内容又会稀释真正重要的部分。

实际使用时，我更倾向于三种方式。

第一种是**让 Agent 自己调查**。当我们不知道哪些文件相关时，不要随便把整个目录扔进上下文，而是先要求 Ask 搜索入口，并说明判断依据。

第二种是**提供自己确定相关的精确位置**。如果已经知道问题来自某个函数、文件或目录，直接引用它，能减少 Agent 走偏。给一个 200 行的相关文件，通常比给整个 `src/` 目录更有效。

第三种是**提供运行状态**。只给静态代码，Agent 看不到用户操作、网络返回和状态变化。报错堆栈、控制台日志、截图、测试结果、复现步骤都属于重要上下文。

例如“页面打不开”几乎没有可用信息，下面的描述就好很多：

```text
运行 `pnpm dev` 后首页正常，但进入 `/categories/AI` 返回 500。
控制台错误是：……
问题只在分类名包含大写字母时出现。
相关路由是 `src/pages/categories/[...category].astro`。
请先复现并解释原因，再修改。
```

这里同时给出了意图和状态。Agent 不必花大量时间猜“打不开”到底是构建失败、路由错误、浏览器异常还是网络问题。

还有一类信息是约束。例如不能增加依赖、不能改公开 API、必须兼容某个版本。这些约束最好在开始时写清楚。等 Agent 已经按默认方案完成后再补充，往往意味着重新实现。

## 验收标准比提示词技巧更重要

很多人研究怎样写提示词，却很少在任务开始前写验收标准。对 AI 编程来说，后者通常更有用。

“完成登录页面”看似清楚，实际上还有很多没有说明的地方：是否要校验邮箱格式，提交时是否禁用按钮，接口失败怎样提示，键盘能不能操作，移动端是否可用。Agent 可能做出一个外观完整的页面，然后认为任务已经结束。

验收标准就是把“我心里默认应该有的东西”明确写出来。

一个小任务不需要复杂格式：

> 修复文章日期显示时区错误。验收：相同日期在本地开发和生产构建中显示一致；不要改变文章 Frontmatter；运行构建确认通过。

一个稍大的任务可以写成：

```text
目标：为文章列表增加搜索。

范围：
- 搜索标题和正文；
- 只做本地搜索，不增加后端服务；
- 不调整文章 URL 和现有分类逻辑。

验收：
- 输入中文或英文关键词后显示匹配文章；
- 没有结果时显示空状态；
- 清空关键词后恢复完整列表；
- 分类筛选和搜索可以同时工作；
- 移动端输入和结果列表没有布局问题。

验证：
- 运行类型检查和生产构建；
- 在浏览器中检查命中、未命中、清空和组合筛选；
- 最后说明修改文件、验证结果和仍然存在的限制。
```

这里没有规定具体算法，也没有告诉 Agent 每个文件怎么写。实现空间仍然交给它，但“什么叫完成”已经比较明确。

验收标准还有一个好处：它会反过来帮助我们发现需求本身的问题。如果自己都无法说明怎样算完成，那么任务可能还不适合进入 Agent，而应该先继续调查或规划。

## 用证据验证 Agent 的结果

Agent 修改了代码，不代表任务完成；构建通过，也不代表功能正确。

不同类型的任务需要不同验证方式：

- 工具函数和数据转换，适合运行单元测试并检查边界输入；
- 类型或构建问题，适合运行类型检查和生产构建；
- 页面功能，除了构建，还要在浏览器里实际操作；
- 视觉修改，需要检查不同窗口尺寸和交互状态；
- 难复现 Bug，需要按原步骤重新复现，并确认日志中的错误路径不再出现；
- 性能优化，需要比较修改前后的数据，而不是凭感觉说“更快了”。

一个很小的例子：让 Agent 修改按钮颜色。如果颜色来自主题变量，只查看组件 Diff 可能看不出最终效果；打开浏览器检查更直接。新版 Cursor 的 Design Mode 还可以直接选择页面元素、框选区域或对着界面描述修改，[让视觉反馈指向具体元素](https://cursor.com/changelog/3-0)，避免反复解释“右上角那个按钮”。

验证也应该包含 Diff Review。测试只能说明已经覆盖的行为没有失败，不能说明修改范围合理。审查时至少看几件事：有没有改到任务之外的文件，有没有重复项目已有实现，有没有为了绕过错误而关闭检查，有没有留下调试代码，新增依赖是否真的必要。

我现在更希望 Agent 最后给出一份简短的交付说明，而不是只说“已经完成”：

```text
完成内容：
- 增加文章搜索索引；
- 在文章列表接入搜索框和空状态。

验证：
- `pnpm build` 通过；
- 浏览器检查了中文命中、英文命中、无结果和清空搜索；
- 在 390px 宽度下检查了布局。

限制：
- 当前使用简单文本匹配，不支持拼音和模糊搜索。
```

这种输出的价值在于可检查。我们可以很快判断它到底做了什么、验证到什么程度，以及哪些事情还没有解决。

## 完整案例：增加文章搜索

把前面的内容放在一起，完整流程并不复杂。

第一步是调查。先用 Ask 找出文章如何读取、列表如何生成、内容是在构建时还是运行时可用。要求它列出相关文件，不修改代码。这一步解决项目状态问题。

第二步是规划。让 Plan 比较适合当前静态博客的实现方式：生成轻量索引还是加载完整正文，要不要引入搜索库，中文匹配能做到什么程度。确定方案后，把不做的内容也写清楚，例如第一版不支持拼音、不接入远程搜索。

第三步是定义验收。搜索要支持什么字段，空结果是什么样，是否和分类筛选共存，需要在哪些窗口尺寸下检查。这里解决“完成”的定义。

第四步才是执行。让 Agent 按确认后的计划修改代码、运行检查。如果执行中发现文章正文无法按原计划生成索引，要求它停下来说明，而不是自行扩大范围重构内容系统。

第五步是验证。运行类型检查和生产构建，在浏览器中输入几个真实关键词，检查命中、未命中、清空、分类组合和移动端布局。对于页面细节，可以直接在 Design Mode 里选择元素反馈。

最后审查 Diff 和交付说明。如果只是第一版搜索，就接受简单匹配的限制，不要顺手让 Agent继续加入高亮、搜索历史、快捷键和复杂排序。把一个边界明确的版本做完整，通常比在同一个任务中不断追加想法更可靠。

这套流程的重点不是每个任务都必须走七八个步骤，而是把不确定性放在正确阶段解决：项目事实用调查解决，技术选择用计划解决，代码实现交给 Agent，运行问题用 Debug 和日志解决，最后用验收标准判断结果。

## 一套更实际的使用习惯

不需要为了使用新 Cursor，一次把所有功能学完。先改变几个日常习惯，效果会更明显。

遇到陌生代码，先要求只读调查；任务涉及多个模块，先看计划再执行；交给 Agent 的工作尽量能够独立验收；开始前说清不能改变的东西；完成后要求运行相应检查；对于页面和交互，查看实际结果，不只阅读代码；最后审查 Diff，而不是因为测试通过就全部接受。

可以把它压缩成一句话：

> 先让 Cursor 理解真实项目，再让它按明确目标执行，最后要求它用证据证明结果。

Cursor 变得更主动，并不意味着人只需要写一句话然后等待。人的工作正在从逐行告诉工具“怎么写”，变成定义“做什么、不能做什么、怎样算完成”。这部分判断越清楚，Agent 能够接管的过程才越多。

这比研究几个固定提示词更难一些，但也更接近 AI 编程真正能够提升效率的地方。
